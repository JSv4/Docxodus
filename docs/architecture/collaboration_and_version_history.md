Proposed shared design for [#671: collaboration](https://github.com/JSv4/Docxodus/issues/671) and [#672: version history](https://github.com/JSv4/Docxodus/issues/672).

Implementation is proceeding through separate PRs, with GPT-5.6-sol review and user merge between each. Performance figures below are proposed gates, not measurements.

The first PR adds [`PackageChangeSet`](../../Docxodus/History/PackageChangeSet.cs): immutable changed-entry payloads, existing OPC digest guards, and atomic apply/invert for imported versions and package fallbacks. It preserves uncompressed entry bytes; exact snapshot storage, the durable codec/blob-store contract, identity sidecars, and fine-grained session recording follow in subsequent PRs. This primitive does not yet provide durable history or collaboration.

`PackageChangeSet.Create(before, after)` captures a contribution, `Apply(before)` reconstructs its target, and `Invert().Apply(after)` reconstructs its source. Inputs must pass bounded OPC manifest inspection. Replay emits stored ZIP entries so reconstruction avoids recompression and remains readable under the same expansion limits; its temporary output can be larger than a compressed snapshot. Exact version export will return separately retained snapshot bytes.

Use **one durable change log, lossless checkpoints, and one replay engine** over `DocxSession`. Both individual edits and imported document versions produce the same committed-change format. History reconstructs an earlier log position; collaboration streams new entries and reconciles pending edits. `DocxDiff` continues to own semantic comparison and Word redlines.

For collaboration, choose a **host-controlled ordering authority per document**, with optimistic local editing and operation rebasing. The authority can run in a server or a designated local peer; storage and transport remain replaceable. This requires an authority to finalize shared edits, while disconnected clients retain local work. It avoids introducing a second rich-document model. The ordered-authority/rebasing pattern has an established [reference in ProseMirror](https://prosemirror.net/docs/guide/#collab); the proposed package operations and conflict rules here belong to Docxodus.

Current code supplies useful foundations, but these are the gaps that determine the design:

| Existing owner | Reuse and required change |
|---|---|
| [`DocxSession`](../../Docxodus/DocxSession.cs), [`mutation contract`](docx_mutation_api.md) | Keep package mutation, optimistic guards, and atomic semantics. Add serializable commands and a commit recorder beneath all public surfaces. Current batch callbacks/results do not retain a replayable request. |
| [`UnidHelper`](../../Docxodus/UnidHelper.cs), `Save(bool)` | Existing IDs help address live nodes. New nodes can receive random IDs; clean saves strip IDs; identical content can collide across stories. Persist collaboration identity separately and record generated values. |
| [`editor.ts`](../../npm/src/editor.ts) | Reuse span edits and incremental reconciliation. Typing currently commits on blur; collaboration needs input/composition commits and selection mapping. `onEdit` is not a complete mutation feed. |
| [`PackageManifest`](../../Docxodus/Verification/PackageManifest.cs), [`PackageDelta`](../../Docxodus/Verification/PackageDelta.cs), [`delivery contributions`](../../Docxodus/Verification/DeliveryReceiptInputs.cs) | Reuse identities, package inspection, normalized-operation vocabulary, and receipt integration. Manifest deltas describe differences; they lack the payloads needed to apply them. Receipts are evidence, not the replay engine. |

The shared contract has three immutable records:

| Record | Contents |
|---|---|
| `Commit` | Schema/codec version, document ID, epoch, assigned sequence, previous commit hash, operation ID `(actorId, actorSequence)`, request fingerprint, original base sequence and pending dependencies, authenticated application actor, revision-author metadata, recorded timestamps, normalized intent, accepted effects, inverse data, position/identity maps, before/after state roots, optional conflict or restore links. |
| `Checkpoint` | Log sequence/hash, state root, complete clean DOCX blob, digest-bound identity sidecar, allocator state, and references to retained conflict/rebase metadata. |
| `Version` | ID, parent version ID, log sequence, exact DOCX blob digest/length, author, timestamp, label/message, application metadata, optional `restoredFrom`. Snapshot identity is SHA-256 of the exact DOCX bytes; distinct version IDs may reference identical snapshots. |

`Commit.effects` is a small, versioned lossless patch vocabulary: XML text/attribute changes; node insert/delete/move or subtree replacement; part add/replace/remove; content-type and relationship changes; and binary blob references. Preserve unknown XML and opaque parts. Include expected old values/hashes and all cross-part dependencies so application is atomic. Keep large inserted/deleted payloads as content-addressed blobs; inverse records can refer to those same blobs.

Separate **intent** from **accepted effects**. Intent is what gets rebased during collaboration. Effects contain the actual XML, identifiers, author/date values, relationship allocations, and derived changes accepted at that sequence. Replay applies effects; it never reruns a clock, random allocator, markdown parser, or an evolving high-level command. Keep readers for retained codec versions; an unsupported version produces a typed error before mutation.

Use a versioned incremental tree digest (`stateRoot`) for live replay checks, including package structure, modeled XML, opaque payloads, and identity state. Do not relabel it as an existing package digest. At checkpoints and named versions, compute the existing raw-byte and ordered-OPC digests independently. The raw digest binds exact downloadable bytes; the state root verifies the live model; neither substitutes for the other.

Persist stable `partId`/`nodeId` values in a sidecar bound to the checkpoint digest. On first open, the authority assigns them once; later IDs derive from operation identity plus a creation ordinal. Rehydrate the sidecar against exact checkpoint bytes using part URI and structural locations, checking the digest first. Map these IDs to current public anchors; descriptive prefixes such as `hdr1` and `h` are not identity. Clean DOCX exports and version metadata remain separate unless the host explicitly requests embedded provenance.

Text positions use `(nodeId, baseSequence, UTF-16 offset, affinity)` plus pending-operation dependencies. Each splice, split, merge, and move supplies a position map. Split retains the first paragraph ID; merge records the absorbed paragraph's mapping to its survivor; moves retain identity; deletion retains tombstone information. Map comments and selections through the same machinery. Respect surrogate boundaries and atomic field/note carriers. Retain historical maps so a reconnect cannot silently address a different range.

Capture changes at the core mutation boundary, covering direct .NET calls, WASM/npm, and agent facades. Each operation family declares its read/write footprint and emits precise effects; shared XML and OPC mutation helpers record inverse values, relationship topology, and dirty nodes/parts. Publish only a successful outermost commit. Rollback discards its provisional record; ordinary no-ops create no state entry. Shared-session raw OOXML operations use an exact-base package contribution when their footprint cannot be safely narrowed.

This needs a lightweight transaction path. Today, `BeginTransaction` clones a full package, ordinary undo clones many XML parts, and `ExecuteBatch` additionally scans review data and serializes/hashes the package. Preserve those API contracts, but let journal-enabled operations use their effect/inverse recorder for rollback and optimistic rebasing. Full package capture remains a fallback for raw operations until instrumented; it cannot be the typing path. Treat render/projection identity bookkeeping as sidecar work, not a user mutation. Reuse recorded effects to update anchor indexes, state-root ancestors, and the editor's affected scopes.

An externally supplied version enters through a second producer: inspect both packages, retain the exact supplied snapshot, and create a lossless contribution for changed entries/relationships with their payloads. Start with changed-part replacements and deduplicated asset blobs; use finer XML patches where identity correspondence is proven. Ambiguous correspondence creates an explicit identity boundary. This operation requires its expected head and conflicts with overlapping pending edits; a pairwise diff cannot recover edits that happened between the two supplied versions. Generate semantic summaries/redlines lazily through `DocxDiff`, never use its renderer edit-script JSON as a general package patch.

The collaboration protocol is `connect/checkpoint`, `submit`, `readSince/subscribe`, and ephemeral `presence`. `actorId` identifies a unique replica, independently of the application user, so two tabs/devices cannot reuse operation IDs. A client persists its actor sequence, acknowledged base, and pending outbox before advertising an edit as locally saved. It sends normalized intent with the base sequence and dependencies on its earlier pending operations. The authority deduplicates by operation ID/fingerprint, maps intent over intervening accepted changes, checks semantic preconditions, and atomically appends the resulting commit. Transport arrival time and actor clocks do not determine causality; assigned sequence and dependencies do.

Clients maintain an acknowledged state plus a bounded optimistic overlay. On receiving accepted commits, unwind pending effects, apply contiguous accepted effects once, then rebase/reapply pending intent and selections, recognizing acknowledgements of their own operations. A single implementation of these rules lives in the core/WASM kernel. Buffer out-of-order messages and request gaps; repeated IDs with different fingerprints fail explicitly. A lost acknowledgement is answered from durable deduplication records, including after restart. A crash after durable append is recovered by replay, before acknowledging new work.

Conflict behavior is part of the contract, not a transport choice:

| Concurrent actions | Required result |
|---|---|
| Disjoint text/ranges, nodes, or independent properties | Rebase positions and apply both; test commutativity at the logical package level, including dependency parts. |
| Inserts at one text gap | Keep both in assigned commit order, preserving each author's attribution; all replicas use the same tie policy. |
| Overlapping deletion | Delete only the originally observed content; concurrent inserted text survives. Replacements with different new text become explicit conflicts. |
| Same property set to incompatible values; delete versus edit | Preserve the accepted state and persist the contender plus its base/branch payload as a conflict. An explicit resolution is a new commit. Nothing is silently discarded. |
| Move versus edit; competing moves | An edit follows stable identity through a move. Incompatible destinations, invalid ancestry, or moves into a deleted container conflict. |
| Lists and tables | Address list instances and row/column/cell IDs, not display numbers or indexes. Recompute derived numbering from accepted order. Independent cell edits and compatible row inserts combine; overlapping merge/split/delete topology conflicts atomically. |
| Notes, headers/footers, comments, tracked changes | Apply owner content, references, relationships/assets, thread parentage, revision groups, and generated-ID mappings together. Concurrent replies retain their parents; reply/delete, shared-story replacement, and incompatible accept/reject operations conflict. |
| Unmodeled/raw package changes | Require unchanged declared package scope; otherwise retain an explicit conflict with the complete candidate contribution. |

A conflict is durable shared metadata with an unchanged package root until resolved; it retains dependent local operations and any referenced assets. The durable sequence is distinct from `DocxSession.Version`, which still counts session mutations. Application actor identity and Word revision authors are separate fields: the host authenticates the former, policy supplies the latter, and replay preserves both.

Collaborative undo is a new compensating commit for the actor's selected intent, rebased over later work. It must not apply an old package snapshot over remote changes. Preserve inserted-content provenance and inverse data so undo removes only the local contribution; undoing a deletion restores its captured content. If later dependent edits make compensation ambiguous, report a conflict instead of erasing them. Redo is another intent commit. Offline/single-user sessions keep their existing bounded undo behavior.

Reconnect requests missing log entries, or a newer checkpoint plus its tail; then rebases the durable local outbox. Archived position maps and original bases remain available for long offline gaps. A reconnect that needs archived history may take longer than a normal open. Compaction must not discard that evidence merely because currently connected clients acknowledged it. If a host explicitly deletes required history, return `history_unavailable` and preserve the local branch for recovery.

Presence uses the same mapped range positions, but travels on a separate throttled channel with actor name/color, connection state, and expiry. It is not stored in commits or snapshots. The browser opts in through collaboration/history options and lifecycle callbacks. Commit text on short input batches and composition boundaries; preserve IME composition and the caret while remote changes arrive. Reuse incremental block/story reconciliation, invalidating dependent lists, note numbering, and pagination where necessary. Bind every editor mutation path, including ribbon, comments, and running stories, through the shared core.

Persistence belongs to the host behind one documented adapter contract; proposed primitives are:

```text
putBlob(digest, bytes) / getBlob(digest)
readHead(documentId)
append(documentId, expectedHead, fencingToken, commit, optionalVersion)
readCommits(documentId, afterSequence, limit)
putCheckpoint(checkpoint) / findCheckpoint(documentId, atOrBeforeSequence)
createVersion(documentId, expectedHead, version)
getVersion(documentId, versionId) / listVersions(documentId, cursor, limit)
```

`append` atomically checks the head/leadership fence, binds the operation ID to its fingerprint/result, and publishes the new head and any restore version. Prepare/apply provisionally under the authority's document gate; publish durable acknowledgement only after append succeeds, and roll back on a failed append. All referenced blobs must already be durable; readers verify their digest and length. `createVersion` similarly verifies the captured head/sequence, allowing a named snapshot without a fabricated content edit. Failed publication leaves only unreferenced blobs for later collection. Provide memory and filesystem reference adapters plus conformance tests and database/object-store recipes; object storage needs conditional head writes or a transactional coordinator. Transport carries this protocol over WebSocket, a hosted service, or a local peer without changing document semantics.

Reconstruct sequence `s` by loading the latest checkpoint at or before `s` and applying its accepted effects through `s`. A timestamp query resolves to the greatest committed sequence at or before the authority's recorded time, with sequence breaking ties. This reconstructs every recorded transaction boundary; unsent/uncommitted edits are only available in their local branch. Named-version retrieval returns the stored DOCX bytes verbatim, even if a later serializer would package the same content differently.

Start checkpoint tuning at **200 commits or 2 MiB of accumulated effects**, plus explicit named snapshots. Materialize checkpoints off the editing path from an immutable captured sequence and publish only once verified; never silently skip a backlog. Chunk/archive old log segments and index checkpoints and timestamps. Cache recent reconstructed states and comparisons. Keep the full reconstruction chain and referenced blobs for all retained sequences; checkpointing bounds normal replay work but does not by itself reduce all-history storage. Physical blob compression/deduplication is host-controlled. Retention deletion is an explicit host policy, not routine compaction.

Restore is an auditable head change: for `V1 → V2 → V3`, restoring `V1` creates `V4(parent=V3, restoredFrom=V1)` referencing `V1`'s exact DOCX bytes. The authority first verifies the snapshot, then atomically appends a restore transition and version using the expected head. Reuse the target checkpoint/state references instead of generating a huge semantic inverse. Advance the document epoch and broadcast the reset. Open sessions install the restored state, invalidate PageMaps/render caches, and retain pre-restore pending work as an explicit recoverable branch; they do not automatically reapply it and undo the restore. A changed head makes the restore request stale and requires a fresh preview/confirmation in the opt-in history UI.

History APIs cover create/list/get/export, materialize-at-sequence/time, compare, and restore in .NET, npm headless, the browser, and Python/MCP integrations. The browser history panel adds browsing, semantic inspection/native redline export, and restore confirmation over those APIs. Version metadata stays outside the DOCX. Key renderer/PageMap/delivery artifacts by exact snapshot digest plus renderer fingerprint and options; they never determine source version identity. Feed delivery receipts from stored normalized intent and accepted outcomes when requested, without constructing full delivery evidence on every keystroke.

Implement in five reviewable milestones:

| Milestone | Deliverable and completion gate |
|---|---|
| 1. Shared kernel | Versioned command/effect codec, sidecar identity, lightweight recorder, apply/invert, incremental state root, and whole-package fallback. Prove replay after restart for every existing editable package family, including generated IDs/dates and untouched opaque payloads. |
| 2. Durable history (#672) | Store contract and reference adapters, checkpoint/reconstruction, exact immutable versions, import producer, lazy `DocxDiff` comparison, atomic non-destructive restore, all headless bindings, and opt-in history panel. History works without collaboration enabled. |
| 3. Two-client kernel (#671) | Ordering authority, durable dedup/outbox, optimistic rebase, text/paragraph rules, restart/reconnect, and selective undo. Ship a transport-free deterministic harness and an in-process/local-peer adapter. |
| 4. Complete collaboration surface | Extend family footprints/transforms to tables, lists, notes, running stories, review data, relationships/assets, and raw contributions. Complete editor input/IME integration, presence, conflict handling, and restore-with-open-clients. A text-only kernel does not close #671. |
| 5. Release gates | Cross-surface adapter/protocol documentation, two-browser end-to-end tests, storage failure recovery, and performance measurements. Close each issue only when its full acceptance suite passes. |

Correctness gates should cover every row of the conflict table with two- and three-client schedules, packet reordering/duplication, dropped acknowledgements, crashes, and offline reconnect across checkpoints. Assert equal canonical package content **and** identity/review topology after convergence; save/reopen and enforce OpenXML validation-delta gates. Test reconstructing every sequence in generated histories against independently captured expected states, not just matching stored hashes. Verify exact snapshot bytes, metadata round trips, corrupted/missing blobs, stale restores, local undo preserving remote work, and untouched media/custom XML. For arbitrary version comparisons, retain the existing `DocxDiff` accept/reject contracts and explicitly surface its existing unsupported/pre-existing-revision limitations rather than claiming byte-reversible redlines.

Performance gates: measure the existing NVCA charter and a large asset-heavy document with 10,000 small edits. Require zero full-package saves/clones/hashes, semantic diffs, or unrelated asset reads on the instrumented typing path; verify counters as well as timing. Target added p95 journal/rebase CPU cost below 10 ms for a small text edit with at most 200 intervening commits on a recorded reference machine; report existing mutation/render time separately. For that same small edit, additional wire/storage data should scale with edited text and metadata, not document size. Measure checkpoint latency, replay tail bytes/operations, restore time, and peak WASM heap; tune cadence from those results. Structural/package imports may cost the size of affected content, and long-offline rebases may scan archived maps—those costs must be reported separately.
